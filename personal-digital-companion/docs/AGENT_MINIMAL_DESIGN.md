## 2. 范围与简化原则

- 单用户、同一账户、多终端；一个云端 Worker 与一个 D1。不建用户管理、多租户、角色权限体系。
- 不为大量并行设计调度平台、队列服务、缓存、负载均衡或实时推送。
- 本线负责任务类型、实际任务、设备识别和后续执行接口；界面线负责设备设定表及任务展示。
- 身份认证保留必要边界；同一个用户不等于接口公开。具体认证方式在骨架阶段核对，不在本次声称已复用现有认证。
- PC 执行与精灵应用生命周期基本绑定，不开发独立于精灵退出后仍常驻的服务。退出应用可中断任务，重开后核对保存记录。隐藏角色与退出应用是否分别处理，留到桌面接线时确认，不能推定所有“关闭画面”都只是隐藏。
- 当前设计对象是任务单元，不在tasklist或tasks中加入前后步骤关系、等待策略或并行调度。链式任务才明确步骤之间的关系，默认等待当前任务执行结束；本阶段不开发链式任务系统。

撤回上一版“任务A等待网络时任务B应先执行”的推定：这属于步骤关系与调度，不能从任务单元定义推导。例：链式任务有A、B两步，默认等A结束才处理下一步；A最终失败也属于结束，但B是否依赖A的成功结果，由链式任务定义，不在本次自行规定。

## 3. 设备识别与设定表

建议首次运行生成固定设备ID并保存在本机，同时提供系统电脑名帮助辨认；通用名由用户标注，存D1的最小 devices 表。未标注显示固定ID，标注后显示通用名，任务归属始终用固定ID。建议通用名唯一，避免派发歧义。

| 固定ID | 系统电脑名（辅助辨认） | 用户通用名 | 展示 |
| --- | --- | --- | --- |
| pc-a81f92 | DESKTOP-ABC | 空 | pc-a81f92 |
| pc-b72e14 | LAPTOP-XYZ | homepc | homepc |

设计意图：改名只改变展示，不使已派发任务找不到原电脑。不建议直接依赖MAC地址，多网卡和更换网卡会增加辨认复杂度。重装后遗失本机ID的处理以后按实际需要确定，本次不建设设备合并系统。

### 网页终端登记与认领（最新确认，待开发）

- 先完成同一用户的登录认证，再检查当前浏览器的终端关联；浏览器标识不是认证凭据。
- 已关联且D1记录存在：沿用原终端ID，显示用户标注的通用名；未标注则显示ID。
- 无关联或对应记录不存在：显示“当前尚未登记终端，是否登记为新终端？”；接受后才创建D1终端记录、分配固定ID并绑定当前浏览器。提示本身不生成记录。
- 不接受新登记：进入终端管理界面，列出本账户已有终端供认领。选择并确认认领后，绑定原终端ID，保留原名称和历史；尚未选择时保持未关联，不偷偷新建。
- 浏览器清理数据后走同一个流程。例：手机原名myphone，清理数据后登录，选择不新登记，再认领myphone；D1原记录和任务归属不变。
- 认领只恢复网页入口关联，不复制或授予PC任务执行凭证，不自动注销其他浏览器、不合并/迁移/删除任务。
- 本线后续负责认证后的登记、关联、认领接口；界面线负责提示和终端管理页面。现有Windows身份模块和设备API不等于已经实现该网页流程；当前未修改代码或界面。

## 4. D1中的两类任务数据

### tasklist：可执行任务类型清单

每种类型一条记录，建议最少包含：

| 字段 | 含义与例子 |
| --- | --- |
| type | 稳定类型，例如 paylog.create |
| name | 展示名称，例如 登记Paylog |
| description | 任务目的，例如 将一笔收支写入指定账本 |
| executor | 执行位置类别：cloud 或 pc |
| parameter_spec_json | JSON参数说明：字段、类型、是否必填；不单独建参数子表 |
| procedure | 执行位置、操作步骤、核对方法等具体文字说明 |
| report_spec | 如何报告成功、失败、缺参数及结果内容 |

tasklist是数据定义，实际执行仍由固定代码按type分派；修改说明不能产生任意脚本执行能力，风险规则由受控工具实现决定。不做可编程流程引擎、插件市场或流程编辑器。

例：paylog.create 的流程可描述为“云端调用已配置的Paylog接口，检查必填参数，满足该工具授权要求后登记，核对返回结果；成功报告记录编号和摘要，失败说明原因”。这只是设计例子，实际服务位置、字段和授权在开发该类型时核对。

例：reminder.create 表示“登记提醒”，创建提醒记录成功后本次登记任务就完成；等待提醒时间不占用当前登记任务的执行位置。提醒触发实现不在本轮范围。

### tasks：每一次实际派发

建议最少包含：task_id、type（关联tasklist）、target_device_id（云端任务为空）、params_json、status、attempt_count（已开始的执行次数，初始0，最多2）、created_at、result_json、error。

例：

```json
{
  "task_id": "t001",
  "type": "paylog.create",
  "params": {
    "date": "2026-11-18",
    "amount": 1200,
    "currency": "JPY",
    "description": "午餐"
  },
  "status": "PENDING"
}
```

设计意图：tasklist解释“这类事怎么做”，tasks保存“这次具体做什么”。列表可组合显示“登记Paylog · 午餐 · 1,200 JPY · 待执行”，不重复复制整段流程。参数统一JSON保存，类型定义也在D1统一读取。本阶段不开放任意修改已有类型标识和执行语义；以后如需变更流程，另行明确待执行任务的处理，不提前增加版本平台。

时间存UTC，展示用Asia/Tokyo。首次创建与查询阶段只产生PENDING；完整状态、执行记录、来源、到期、领取防重复与恢复字段在领取执行阶段按V1.5补齐，不表示取消原需求。

### 任务单元结束与重试规则（用户明确）

- 首次执行成功：COMPLETED，任务结束。
- 首次执行失败：立即重试一次，使用同一个task_id、同一份参数；不创建第二个任务，不增加等待退避或可配置重试平台。
- 第二次执行成功：COMPLETED，任务结束。
- 第二次仍失败：FAILED，任务结束，不自动进行第三次执行。
- 首次失败到重试期间仍属同一任务执行过程，不提前记作最终FAILED或通知链式任务“已结束”。每次执行保留执行记录；重启不能把已用次数清零。

例：查询C盘首次失败，立即重试；第二次成功则报告结果，第二次失败则报告“执行两次均失败”及原因。无论最终成功还是失败，该任务单元都已结束。

写入类工具沿用已有幂等/结果核对要求，例如登记Paylog重试仍对应同一笔登记；请求超时且结果不明时先核对是否已写入，不能把回执丢失直接当成可重复新增。此要求属于具体工具正确执行任务的细节，不引入链式任务机制，也不增加第三次执行。

## 5. 最小接口建议与开发影响

| 接口建议 | 用途 | 所属后续阶段 |
| --- | --- | --- |
| GET /api/tasklist | 获取任务类型、参数说明、流程与报告要求 | 任务创建与查询 |
| POST /api/tasks | 按已有类型、目标、JSON参数创建任务 | 任务创建与查询 |
| GET /api/tasks/{id} | 查询任务并关联类型名称、说明和结果 | 任务创建与查询 |
| GET /api/devices | 提供设备设定表数据 | 设备识别与接入 |
| PATCH /api/devices/{id} | 保存用户标注的通用名 | 设备识别与接入 |

初期任务类型通过明确的初始化SQL写入D1，不开发tasklist增删改管理界面或接口。创建任务检查类型是否支持、JSON参数是否符合该类型的必要约束、PC目标是否有效；查询不存在的任务返回未找到。实际领取、执行、回传接口留到对应阶段。

本线受到的影响：

1. M1-01骨架保持一个Worker和一个D1，数据范围增加tasklist；不恢复复杂用户/会话体系。
2. M1-02由“直接传工具名称”调整为“选择D1中的任务类型并传JSON参数”；创建前读取类型定义，查询时关联名称及说明。先用disk.query验证链路，Paylog和提醒只是类型设计示例，并未授权本轮实际开发。
3. 后续Windows执行不再采用独立常驻生命周期；按应用退出可中断、重开核对的方向设计。设备命名需要最小devices数据和接口，具体实现分配到后续批次，不能塞进当前第1项。

最新补充影响：tasks需记录已执行次数，后续执行器落实最多两次执行及最终状态；tasklist不增加任务间等待字段。本次不扩展到链式任务开发。

### 待开发：链式任务（第一轮明确不处理）

- 状态：待开发，后续另行安排，未获准开始实现。
- 范围：描述任务单元之间的步骤关系；默认等待当前任务执行结束。
- 已确定的基础：单个任务首次失败立即重试一次，第二次失败也属于任务结束。
- 后续设计时再确定：上一步失败后下一步如何处理，以及步骤间需要传递哪些结果；本轮不推定这些规则。
- 例：先查询数据，再依据查询结果执行登记，两步关系属于链式任务；查询和登记各自仍是独立定义的任务单元。
- 第一轮不建链式任务表、接口、步骤依赖或调度机制，不以预留名义加入这些实现。
