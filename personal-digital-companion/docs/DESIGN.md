## 手记整理的固定 8K 路线（2026-11-23 JST）

依据 [用户原话](../REQUIREMENTS.md#手记整理的双-4b-与到点启动2026-11-23-jst)、项目 [备忘录索引](TASK_TEMPLATE_PREVIEW.md)、[最简设计](AGENT_MINIMAL_DESIGN.md)、[任务边界](AGENT_CHAIN_DESIGN.md) 与全局 `G:/selftool/resourceforlater/docs/FRAMEWORK_PREFERENCES.md`。索引未指向独立开发设计备忘录。复用手记现有调度、模型进程和草稿表，沿用单人自用、按需装载及东京日期。

- 普通手记和积压补记使用同一条成文入口。现有积压量只区分普通成文与分主题归类，到期后不因件数少延后。没有未入册材料时不进入成文入口。行动补评、其他本机任务与前台对话仍用所属流程。
- 每项开始时检查 GPU 并实装 4B，CPU 辅助也用 4B。每个成文进程固定 8,192 token。GPU 不够时释放当前 GPU 模型，用 CPU 4B 走清洗与绯月成稿。CPU 辅助不能装载、GPU 可用时，单 GPU 4B 走同样两步。都不可用则保留原材料，等待后续轮询。
- 以单次输入 4,761 token 和最多生成 1,843 token 配置，按实际模型分词并为后续步骤携带前稿留空间。普通记录整条贪心追加，下一条放不下就从下一片起。单条整放仍超限才按自然边界拆；自然边界不可用时按 Unicode 字符拆，避免静默丢资料。结果按片序合并，短评与对应正文一起保存；超过已有的 5,000 字篇长时按顺序存为多篇，全部分篇的本机草稿同一事务保存。保留资料日和叙述日；只在语义明确时转成相对日期。字数指导不触发截断或返工；真实推理或格式失败可直接简述一次，仍失败时本项留待处理。
- 复用询问池占用两路时隙处理一项整理任务。普通停止只影响准入，已开始的项继续到合并；需要交出模型时等当前项生成完成。业务侧先写草稿，再响应停止。关闭应用使用询问池的结束信号，允许取消在途模型调用，已保存草稿保留。未合并的内存片段不提前标记已入册。

## 本机 AI 单项与整轮执行时钟（2026-11-23 JST）

沿用全局框架偏好 `G:/selftool/resourceforlater/docs/FRAMEWORK_PREFERENCES.md` 和项目最简设计 `docs/AGENT_MINIMAL_DESIGN.md`、`docs/AGENT_CHAIN_DESIGN.md`。按 `docs/TASK_TEMPLATE_PREVIEW.md` 的索引复用现有询问池、业务检查点和轮询器。

- 在主力和辅助模型真正调用推理时启动单项时钟，返回或取消即停止。每次尝试与其耗时在同一事务保存。补评按原材料归并各分片，持久化的已耗时间跨重试和正常重启有效。旧记录从升级后首次执行开始计量。达到 120 秒的项目取得终止回执，补评保留原材料并记录丢弃，手动扫描同样跳过它。
- 整轮时钟只累计 4B 执行。在 30 分钟前进入询问池的项目可以继续审核、返工和处理同一材料的分片。达到 60 分钟时共同的取消信号打断两路在途工作。已完成阶段继续有效，整轮中断的项目可在下轮续办。
- 短判断和简审优先交给 CPU 2B，简审排在代写之前。主力优先处理长稿、日记、唠叨、精度敏感阶段及定稿。成批补评时为审核预留 CPU，主力硬件无法执行时，符合长度和内容条件的短评级仍可交给 CPU 代写。内存不足时由 4B 承接适合的步骤。
- 执行期间冻结轮询和等待队列的复查计时。最后一个执行者释放后，从剩余间隔继续。前台真正提问仍可打断后台，开着面板可继续整理。询问池自身负责推进已领步骤。运行日志的 `duration_ms` 是该步经过的时间，`inference_ms` 是该次推理耗时，`task_execution_ms` 是该任务截至本次的累计执行耗时。

### 桌面的一次学习

从绯月菜单「陪我学习」或明确的对话请求进入同一个月印面板。首屏显示继续上次、语言对练和题库练习。选中场景或题库后才加载正文、附件和历史。离线时列出已有缓存，空库给出选择其他来源的入口，取材失败可重试。复盘用东京时间显示场次，每条建议能点回作答证据并重练。

| 入口 | 作答与总结 |
| --- | --- |
| 照剧本练 | 取已有场景和完整对话，保留前文、A/B 身份和台词顺序。A 给出情境，B 拼词或手打；订正时可看参考句。考查独立表达时先隐藏参考句。总结列出任务完成情况、一个值得改的表达和可重练的轮次。 |
| 自由对练 | 本机模型演 A，根据 B 的实际回答接话。能听懂就继续，确实影响沟通才在角色内追问。收尾后区分自然替代表达与有证据的错点。听写可选，先核对转写；模型或语音不可用时可切回文字剧本。 |
| 抽题练习 | 复用知序的启用题、标签、未做或待复习筛选。在候选池内抽 N 道，同套去重，不足时显示实际数量。提交后用原题答案和解析判分，复盘分列错题、未答、反复误选的选项及下一组练习。 |
| 模拟考试 | 普通模考沿用知序的 60 分钟、随机最多 70 道、达到 90% 合格以及暂停恢复规则。固定开考试卷及选项顺序。考中仅给题面、导航、计时和标记；交卷后开放解析。可另选按弱项抽题的「强化测验」，单独标识成绩。 |

### 强化怎样抽题和降频

建议对每个薄弱点使用四档相对权重 1、3、5、7。仅在强化抽取时采用，先按原规则筛选，再按相对权重无放回抽样。语言分别追踪原句和有明确依据的考点，候选取原句与命中考点中的最高档，避免同一错误重复放大。题库按原题追踪；同标签用于寻找变式，其他题各自验证。固定剧本在场景内按原顺序演，强化影响下一次选练的句子或场景。

| 场次中的证据 | 下次如何处理 |
| --- | --- |
| 首次有效作答确错 | 对应目标升一档，到 7 封顶，独立连续计数清零。同一场、同一目标最多一次升档；当场重复订正保留作答明细。 |
| 独立答对 | 首次作答、未获提示、未看答案且判定明确才算。一次场次同一目标最多计一次；有确错的场次按错结算。连续三个有独立证据的场次答对才开始降一档，此后每个独立答对的场次再降一档，最低为 1。关窗续练沿用原场次。 |
| 没把握、看过答案或未答 | 蒙对仍按题库规则给分。点「没把握」即进入下次待验证清单；在已选范围内有名额时先安排一次，避免普通权重的疑点一直抽不到。提示、订正、跳过、断线和待核对只保留事实，均不推进独立计数。 |
| 易混对照 | 优先选有依据的同考点变式。如分别用「で」回答活动地点、用「に」回答存在地点；或用另一道现有题区分反复误选的两个概念。有材料时用换情境作答验证迁移。只有原题时显示实际进度（如「原题独立答对 1/3，换题待验证」）；达到原题掌握条件后才显示「原题已掌握」。 |
| 判错有疑问 | 对练标「这句也成立」或「听写有误」时保留原话，立即撤掉争议作答对该目标的影响。可核对后确认原判或改判，再按顺序重算受影响目标。题目标「有疑问」后退出本机强化候选，核清后恢复，历史试卷保留原快照。 |

每次作答保存来源、场次、题目或剧本轮次及版本、首次答案、提示使用、结果和可选反馈；用稳定作答编号去重。单独保存可选反馈有助于区分“正式得分”和“还想再练”。同一单据经中继取得回执后只关联原记录。题意或正确答案发生变化时保留旧成绩，新版本重新验证掌握。普通自由聊天、仅有本地分词而无标注的句子、教师推测的错误都不能单独作为考点加权证据。

自由对练收尾时，可从原句选择「验证这个表达」，取现有材料中目标明确的小题，依据该题的独立作答决定是否强化。找不到适用材料就保留疑点，复盘仍能回到原句。没有证据的场次保持既有验证进度。同场同目标有多次独立作答时，已确认的错误优先，当场重试仅作订正。正式考试中「没把握」只是用户自己的标记，正确性、解析、推荐练习及相关模型点评均在交卷结算后显示。

## 正向与负向激励库

2026-11-23 JST。依据[用户原话、后续确认及 K1～K9 验收标准](../REQUIREMENTS.md#正向与负向激励库)。一期以本机知识库完成从查询、发现缺口、用户修正到下次应用的完整流程。以下库表、匹配方式和界面接线属于设计选择，待实现验证。

### 一次疑问如何处理

1. 绯月在普通问答、主动提问准备或任务判断中发现信息不足时，从当前入口允许使用的材料提取对象、意图、已知条件和缺口。先用标题、别名、情形关键词查本机 SQLite，再结合原句与上下文核对少量候选。复用本地模型理解不同措辞；有歧义就保留独立实例。直接读取用户已经指定的条目时可跳过匹配。
2. 从生效的正向卡取出定义和适用的“条件 → 做法”。生成答复或采用某个做法前，按当前情境检查生效的负向规则、例外和替代做法，即使正向库尚无对应卡也要检查。例外成立就按实际条件重新选做法。缺一个事实时只问该事实；已生效的规则在当前条件下仍互相矛盾时，展示两条供裁定，暂缓有冲突的动作。
3. 命中可行办法后，用原任务入口尝试处理，继续遵循原业务的能力、授权和回执规则。只有查后仍缺解释或适用案例的独立事件才进入正向计数。负向计数要求有具体错误做法及纠正依据。缺少能力或工具超时本身不能推出一条用户偏好。
4. 对明确的长期纠正，按用户原话及其直接表达的条件，在一个事务内新增或修订生效负向卡、记录来源。提交成功才回执，回执可打开该卡；同一来源重放返回原回执。只有当次反馈时走负向实例计数。范围说不清时可追问，模型推测的范围只能作为草稿。

### 一期应用流程接线

桌面主进程 `desktop/shell.mjs` 在取得 `profile` 后创建一个知识库实例，显式传给问答宿主、主动提问和任务拟稿入口。界面编辑与自动查询共用该实例。宿主接收当前业务判断、可用证据和稳定来源编号；只有需要理解、选择做法或准备追问时才查库。天气实况、时间、菜单跳转等确定操作沿原有快捷路径。后台巡检沿用已有时隙，模型只核对命中的少量候选。用户直接说出的长期纠正在本轮本机处理并回执，无需等待关窗转录。

| 用户或绯月正在做什么 | 在现有流程中的落点 | 采用检索结果的方式 |
| --- | --- | --- |
| 普通气泡、便签或直连发言 | `screen-question-host.mjs` 的 `submitThread` 先保存消息。由 `conversation-thread-replies.mjs` 的 `answer` 在实际回复分支处理，引用和显式命令仍交原处理器。 | 在本机生成回复前读取条件、案例与例外；临近要追问时用已知条件复核。能自行解答就直接回答，有实际缺口才记录并询问。批量发言逐条辨认纠正与一次性说明，保留各自来源。 |
| 截图、附件或独立问答路径 | `screen-question-host.mjs` 的 `ask/perform` 在完成原入口许可的资料识读后，进入文本判断或本机直连前调用同一实例。 | 知识帮助解释已经读到的事实。无法识读、网络错误、用户取消按原入口报告。单纯读取引用、按钮确认等确定操作不作学习样本。 |
| 绯月准备主动提问 | `personality-nags.mjs` 的 `poll` 在拟出有依据的问题后、`enqueue` 前查询；`pollAudit` 对 `audit.prepare` 返回的候选在 `queue` 前查询。场景、专题恢复及主动交流在 `shell.mjs` 接到 `nags.enqueue` 之前使用同一判定。 | 比对真实来源、具体未知点与适用案例。只有知识能解释当前疑点且当前事实已知才抑制提问。必须向用户核实的事实照常入原待答队列；分享和关心经原交流路由。 |

显式业务命令由真正拟稿的入口读库。上游的路由、模型排队和底层工具请求不再分别计数。知识卡内容作为本机判断材料，宿主只接受现有动作和字段。页面确认或修改提交成功后，下一次判断重新读生效版本。

**反馈与重试。** 对话线用已保存的用户 `message.id`，`runThreadCommand` 向实际处理器透传这个编号。独立 `perform` 第一次受理时保存原始编号到请求，重试时取回该编号；现有每次尝试新建的 `turn.id` 仅用于该次执行。转录用原发言的来源编号，后台轮询用稳定的来源类型、对象编号和具体问题点。追问或“刚才那次错了”回指被纠正的原决定，同一决定收到两次相同反馈只算一次；两个不同决定即使文字完全一样也可分别计数。来源及问题点在首次判定时固定，后续复用。回放、摘要、重开、模型自己写的回复或草稿里的引用不能触发长期纠正。只认用户本轮直接表达的意思，混合指令分别交给知识库和原业务入口。

**主动提问结果。** 在各自已有的异步准备阶段等待查询，保留 `enqueue` 同步布尔契约。调用方分别处理“本机已解”“仍需用户”“延期”。已解时保存该来源、问题点和所用修订号，结束本次候选，不发送题目、不伪造用户回答。已核查的同一来源和规则版本下次轮询可跳过，来源事实或规则有变化时重查。场景的 `deliver` 和主动交流的 `choose` 需要区分已解与已入队，专题恢复沿用实际用户作答契约。待答队列满时继续暂停原有后台拟题；前台及其他已受理的独立事件仍可累计并建知识卡。追问阶段（含 `threadAnswer` 和旧气泡 `reply`）也按此规则检查缺口与接收纠正。

转录拆段时把原始发言编号随每个片段传入。现有 `transcribeThread` 给片段生成的 `sourceId` 只定位引文；计数回到原发言所指的独立事件和问题点。三个片段描述同一决定时合计一次；用户明确叙述三个可分别定位的决定时可分别计数，依据不足时保留一次。前后台各自处理同一发言也共用这个键。

**本机边界与故障。** 知识片段、实例、据此生成的本机答复和复核意见只供本机推理。对话线的自动云端回退、独立气泡的云端复审、联网检索及云端拟稿各自检查数据来源；涉及本机规则的判断留在本机。显式业务提交只使用原入口允许且已确认的业务字段。既有不留记录的场景只用瞬时判断。知识库暂不可读时，明确标为查询失败，有赖规则的决定暂停或询问，不记作未命中；独立功能继续。纠正写入失败保留原用户发言供按原编号重试。启动/系统恢复时核对本期备份，跨周期检查复用桌面生命周期，退出或恢复快照前先收齐知识写入。

主动提问还要核对作答后的归档。现有 `personality-diary.mjs` 的 `saveNag` 会落盘整条问答，`syncNags` 可在发布摘要前准备原文附件。查询结果和知识回执只留在知识库；将纠正与普通业务答复按来源分开，允许归档的普通内容继续走原流程。若两者混合且无法可靠分开，保留原业务待处理状态，提示用户单独提供可归档的答复。受限内容在写入问答记录、生成附件或加入待传队列前即隔离，重启补传也沿用该决定。未使用私有知识的正常问答按原契约同步。

### 知识怎样触发外置 Skill 修正

用户要求设计绯月自我修正 Skill 的办法。建议先在本机试点 `conversation-transcription`。外置功能仍在开发，操作能力以[当前手册](SKILL_HOT_UPDATE.md)和[热更新复核](reviews/SKILL_HOT_UPDATE_REVIEW_2026-11-23.md)为基线。下列自动归因、候选生成、隔离回放及启用检查均为拟开发接线。建议让绯月自己拟改和验证，用户在本机确认具体候选后再启用。

1. **从实际错误定位。** 业务宿主在知识实例上附当次实际使用的功能 ID、变体、版本或随附标记、阶段、来源编号、实际提供给该阶段的知识修订及结果。在长期纠正写入、知识卡确认或修订生效时检查关联实例；此后若用户反馈或可核对的结果表明同一阶段仍用错这条生效规则，也可据该事件复查。先核对当时是否确实把适用规则交给了该阶段；漏查或传错版本归入知识接线问题。只有在隔离回放中旧 Skill 拿到正确知识仍可复现错误，才提议改对应阶段。新术语、个人偏好先作为知识应用；缺事实就补问，执行器或能力问题交原宿主处理。第三次建待确认卡本身只触发知识整理；后来的复查不能把单次反馈另写成生效知识。已有同证据、同基线的候选直接打开原提案。
2. **只拟最小修改。** 如用户已教“打算做”和“做完了”应分开，转录仍把计划写成已完成事项，先改 `local-ai.json` 内 `organize` 阶段实际读取的提示，具体例外保留在用户知识卡。仅当问题涉及已支持的步骤或条件时才改 `workflow.json`。首个试点采用当前对话线转录宿主：目录可加载 `SKILL.md` 正文，但此宿主构造阶段指令时读取的是阶段提示与步骤指令。先在隔离调用处比较实际指令或实际执行的步骤；只有正文差异、运行输入和步骤均相同的候选直接结清，免做双版本模型回放。候选附来源卡编号及修订、失败实例、改前改后、期望行为与旧版引用。案例用去标识的等价材料，权限、宿主代码、业务确认和总纲路由继续由程序管理。
3. **隔离比较。** 从实际加载快照派生专属候选，独立资料目录保存机器草稿，保留用户手工草稿。现有 `external export` 用随附模板起草，故须将已激活版本的有效正文、提示和命令链物化为候选基线再改，核对零改动时与运行版本行为一致。用目录工具 `check` 校验，在隔离 profile 分别激活基线和候选，送入同一转录宿主、模型及输入。样本至少包含原失败、已成功正例、例外或近义反例、确需追问的缺项。预先写定可检查的状态、字段与确认结果，案例只到草稿交回，业务写入用隔离替身。原失败须修复，正例与例外保持通过，含糊或不稳定保留为待验证。仅结构校验或模型自评不足以建议启用。
4. **用户看到并决定。** 挂到知识卡详情和「待我确认」中，标示“Skill 修订”，展示原版本、改动、双版本逐例结果、涉及的后续作业和回退目标。可以接受、驳回或继续修改。草稿改变后原回放结果失效。驳回后同一证据与版本不重复提示。采纳知识卡与启用 Skill 是两项独立决定。
5. **启用与回退。** 现有 `publish` 会立即更新 `active.json`，隔离试跑只针对隔离资料目录。正式启用需在发布工具原有锁内重比对当前槽位基线、获准的候选内容指纹，并在知识修订仍有效时发布。基线改变则重做差异及回放。记录前后引用，回读实际加载版本；结果不明先读目录与快照，避免重复切换。在途转录继续使用开工时保存的快照，新作业使用新版。用户报告回归时，从同一提案以 `use` 回到旧外置快照，原来是随附版则 `reset`。回退前核对仍为目标版本。知识周月恢复不切换 Skill；恢复后依据或修订不匹配的候选要重验。

提案状态及其基线、证据引用、准确差异、回放记录和用户决定随知识库快照保存；已发布 Skill 文件继续按现有版本目录管理。用隔离目录从差异重建候选后校验指纹。当知识已停用、回放时能力目录与当前宿主不兼容、候选来自恢复前的旧资料或所用 Skill 回退到随附版本时，先标为待重验。采纳后的自然任务沿既有回执核对同一阶段是否再犯，复发时用新旧版本与该次实例定位，允许从卡片回退。反馈只来自真实用户或已核对的业务结果，隔离回放、模型自评和生成的候选均不写入正负向计数。

**迟到反馈与对照回放。** 转录宿主完成作业时会清除 `job.skill`。因此在交回结果前，将该判断所用的 Skill 引用、内容指纹、阶段、来源编号和实际知识修订随加密的结果保存；沿用原留存期限，无需复制整份提示和对话。反馈到达时按回执找当时的判断；缺证据时标记无法归因。若出错后用户已更新 Skill，先用当前生效版复测；已经修好就结束，仍失败才从当前版拟改。基线、候选分别新建隔离作业，使用相同材料及模型设置，从空步骤记录执行，核对两边实际调用的阶段及指纹。重开旧作业会复用已完成步骤的输出，只用于检验续作契约。

### 本地数据与第三次触发

采用现有桌面运行时的 SQLite 能力，在绯月资料目录中单设一个知识库文件。一个事务可以覆盖两库及它们的关联。首次打开建立空库并记录结构版本。内容按入口权限读取，实例只保留定位来源所需的编号、简短摘录、当时条件和处理结果。

按 2026-11-23 JST 用户追加的可迁移要求，知识库主进程在资料目录使用一份 32 字节随机密钥 `knowledge.key`，两库及自动备份共用。已有库首次读取时可从原 `knowledge-keys/` 目录采用匹配现库的密钥。数据库和备份只存密钥标识。用户原话、标题、别名、案例及实例正文用 AES-256-GCM 加密，每条记录使用独立随机 nonce，并绑定记录类型及编号。来源去重使用带密钥摘要。外层查询字段包括编号、类型、修订、状态和时间。主进程按页解读现有内容，无明文搜索副本。诊断保留编号和失败阶段，用户正文及密钥不进日志或 Git。备份预检实际验证记录，密钥可导出及导入，不依赖 Windows 账户。

| 数据 | 字段与用途 |
| --- | --- |
| 知识条目 | 稳定编号、正向或负向、标题和别名、结构化正文、生效或停用、来源、修订号和更新时间。正向正文含定义与多组条件和做法；负向正文含适用条件、错误做法、原因、替代办法及例外。负向卡可引用关联正向卡的稳定编号。 |
| 疑问或错误组 | 组编号、类型、共同的知识缺口或纠正点、可选原条目编号及基线修订号、处理状态和草稿。前两次只保存实例，第三次将同一组转为待确认卡；修订草稿与原条目分别保存。 |
| 独立实例 | 来源事件标识、问题点标识、类型、所属组、发生时间及简短依据。以来源事件、问题点、类型组成唯一键。跨重试沿用最初事件标识；同一会话确实发生的不同事件可分别计数。计数取实际归入该组的唯一实例数。 |

归组依据是能否共用同一解释或改法。例如“月报尚未定稿放哪里”和“月底报告还在改放哪”可合组，“月报金额如何核对”另组。宿主串行完成归组写入，在事务里去重、插入、核对数量并更新同一组状态。达到三次的同一组只出现一张卡，第四次追加实例。即便期间关闭应用，重放第三个事件也只能得到原卡。知识卡使用自己的待确认视图，现有主动提问的队列名额和同对象限制继续由原入口管理。

用户可编辑定义与案例、缩小负向条件、说明例外或标记实例原因不同。拆开的实例重新分组并按实际数量判定是否达到三次。确认草稿时事务内写入条目、递增修订号并结清该组；以后针对新版发生的新缺口另计。若期间有人已在本机改过原条目，保存前展示现版与拟改内容，让用户决定。明确长期纠正若已解决同条件的待确认卡，一并关联并结清，保留实例。只有已生效的条目供绯月采用，用户停用后下次查询立即排除。

从原条目直接编辑时，详情同时列出挂在旧修订下的未结缺口。用户保存时可勾选本次已经解决的缺口，写入新修订并一并结清；未覆盖的案例保留原实例、次数和待确认卡。前两次的缺口也按此处理。相同问题后来再发生时，依据当时生效的案例判定，不因改标题或修改无关字段重复计数、清空实例或重复建卡。

### 本机页面

由角色或托盘菜单的「知识库」打开共用月印面板。正向、负向、待我确认均支持按词搜索和分页，每页至多 6 条，页码和翻页按钮固定在底栏。切换页签、搜索或改变待确认筛选后回到第一页。首屏读取当前页的摘要，点击再读取正文、实例和关联条目。时间显示 JST，窄窗使用单列。详情可改条件与案例、确认草稿或停用现行规则。空库、没有搜索结果、保存失败分别提示，保存失败保留输入。备份页统一提供一个导入密钥和一个导出密钥入口。换机后先导入密钥，再选择备份文件，预览后确认恢复。

桌面主进程负责读写、按稳定编号与修订号校验操作。面板通过既有 preload/IPC 模式请求列表、详情、保存及恢复。建窗沿用 `desktop/panel-window.mjs`，菜单和共享样式按 `desktop/menu-layout.json`、`desktop/source-updates.mjs` 接线。本期知识库查询、写入及备份全部在本机完成。

界面按用户补充采用藏书室风格。正向、负向、待确认和备份四个页签共享书架画面，以书脊目录卡显示条目和状态。编辑案卷进入详情后再加载，保存与确认固定在底栏。备份页的常用操作集中在同一个工具条，恢复预览并列显示快照与现库数量。书架由 CSS 绘制，沿用桌宠共用颜色、月印标题栏及减少动态效果偏好。

### 周月备份与恢复

- 时间戳存 UTC，周期按 `Asia/Tokyo` 划分，周一为周首。启动及持续运行跨周、跨月时，检查本周期是否已有成功快照。关机错过周期时，在本周期首次运行时备份当时实况。周、月同时到期时可从同一一致性快照生成两份各自管理的副本。
- 用 SQLite 一致性快照生成临时文件，涵盖条目、关联、草稿、实例与结构版本。在独立连接打开副本，通过完整性、关联及同一读取时点的记录数检查后原子落盘。周、月各保留一份，各自有通过验证的当前周期快照后才移除该类别旧快照。内容相同的同一时点只显示为一张周月备份卡。失败保留已有备份，可重试。正式资料随安装版资料目录管理，开发隔离资料不入 Git。
- 密钥和备份分别留存。换机时导入同一把原密钥即可恢复周、月任一备份。已有内容的现库拒绝导入不匹配的密钥。恢复预览校验密文、结构和文件指纹。
- 恢复预览列出快照时间、正负向条目数、待确认数及与当前库的数量差异。用户确认后暂停知识库读写，等待在途写入收齐，验证所选副本的结构兼容、内容可读与关联完整。当前库可读时先生成经校验的恢复前快照。关闭连接后切换到已验证的暂存库，隔离旧库的 SQLite 日志文件，重开复检成功再开放读写。切换异常时可退回原库。
- **现库已经损坏时**，由桌面菜单进入同一恢复入口，独立读取备份目录。预览把现库的不可读数量标为未知。停写关库后，先完整保留可取得的原数据库及配套 WAL/SHM 文件，标明“故障现场，未经完整性验证”。保全失败时保留原件、停止替换。用户确认所选完好备份后按上一步切换；中断重启时先识别留存的原件与已验证副本，恢复完成前禁止自动建空库和轮换旧备份。

### 二期每日同步与服务器修正

一期为条目及关联保留稳定编号和修订号。二期由本机每日同步两库及待修正内容；离线时继续本机工作，恢复连接后补传未同步修订并取回服务器修改。服务器页面沿用相同的条目、草稿和生效语义。同步按编号及共同基线判定变化，重复发送同一修订应得到同一结果。两端从同一版各自修改时保留双稿，用户裁定后产生统一新版。具体同步时刻、实例摘录的上传范围和服务端接口留到二期详细设计。一期不建立远端任务。

## 处理顺序

1. 宿主识别现有模式和入口，读取该场景的 Skill，并固定用户原文、用于日期解析的 JST 提交日期和允许使用的资料。菜单操作和数据读取继续用已知工具。需要模型理解时，主力直接返回该入口所需的答案或结构化草案。
2. 主力按场景复审。对照原文和已经读到的证据，检查意图、关键字段、遗漏、权限与结论。错误反馈交回主力重做，重做后仍须复审。通过后立即交付；明确缺少用户才能提供的资料时，给一个具体补充问题。
3. 主力用尽本类尝试或已无法正常推理时，独立启动升级 9B 和云端候补。两边使用同一原意和适用的复审反馈，分别返回候选。等待两条可用分支返回或有明确终态，保留独立的失败原因。云端沿用现有供应商策略；本机同一时刻仍只跑一个文字模型。
4. 对有结果的候选做**一轮最终复审**。宿主先剔除字段结构、权限、日期或已知证据明确不符的候选。一次复审对其余候选一起判断并择优，返回选中编号和简短依据，或指出所有候选的问题。评价顺序为事实与原意、必需字段的完整性、表达或可执行性。同等可用时采用本地候选。关键事实无法核实时提出具体问题。
5. 一条候补通过就可交付。两条都无法形成可交付结果时，汇报主力卡点及两条候补的原因。取消是独立状态；待确认、待复审或已有写入待回执也各显示真实状态。

拟议的最终复审由可用的本地模型执行，优先主力。主力当前不可用时，使用可用的升级模型。两者均不可用、且资料允许进入现有云端通道时，可由云端完成这一轮复审。宿主先判断复审入口是否可用；一轮复审发生后不另起复审或反复生成。若没有可用复审入口并且有候补结果，显示「待复审」及具体原因，保留原稿以便用户主动重试。

2. 本机用 SQLite 保存会话、作业阶段结果和确认批次。原话和草稿沿用 `conversation-history.mjs` 的加密方式，按来源轮次查证，日志仅输出状态和计数。每一阶段通过固定格式校验后落盘，重试从最近有效阶段继续。候选身份由来源事实和目标共同确定，普通对话转录、显式登记以及重复关窗共用来源去重。用户纠正同一待确认事实时以更新后的正文重新展示。
3. 落盘后通知现有调度入口，并立即尝试入本机正式工作队列。当前 `enqueue` 只排队和安排延迟检查，模型仍繁忙则在现有等待机制中按原编号重试。转录、推理、复核和待确认清单全部留在本机，只使用既有本地模型及本地可用的模板、已缓存目录。缺少目录时保留候选并标明待配置。

### 固定标题和正文

复用[既有助记标题和标记](RECORDING_CHAIN_RELEASE_DESIGN.md#今日任务和绯月助记标记2026-11-20-jst)。本次对照全局与项目开发规则、[开发纪要](DEVELOPMENT.md)和 `G:/selftool/resourceforlater/docs/FRAMEWORK_PREFERENCES.md` 的最简实现约定。按现有索引未找到独立的开发设计备忘录。沿用转录 Skill 同版本模板和已确认草稿的提交流程，由宿主统一排版。

- 个人日记、事项提醒和鱼与熊掌标题统一为 `[十字以内摘要]绯月助记-YYYY-MM-DD HH:mm:ss`。摘要在原有拟稿或逐段补查中给出，程序限制十个可见字符，末尾补会话首条用户发言的东京时间。日记缺摘要时复用已归纳的事项，提醒缺摘要时用正文前十个可见字符，资源缺少主题时保留待补。吃喝、运动和随手记沿用只有正文的字段。
- 正文第一行为固定栏目。个人日记用「记录」，吃喝用「吃喝」，运动用「运动」，随手记和提醒用「事项」，资源用「资源说明」。保留依据充分的内容和必要换行。提醒可另有「准备条件」，仅采用能在原话核对且正文尚未覆盖的前提。网址、分类、感想、到期时刻继续使用各自字段。有正文时最后一行只写一个 ❤️。一键事件仍提交空参数。
- 在待确认清单落盘前排版一次。字段缺失或加标记后超出业务上限时标出待补，保留原文。确认后从已保存的预览参数构建登记链，重启、重试无须重新排版。既有清单按其保存版本读取。

普通气泡由菜单直接以「登记」打开或在下拉选择时，纯文字的差异只在于给当前轮标明明确登记意愿。关窗后仍使用同一作业、模型和模板。整理成果包含一条个人日记，正文保留所有明确登记的原文。同窗自动对话仅追加原本已形成日记的有据内容。吃喝、运动、提醒、资源等仍按原模板判断，已有依赖引用同一条日记。无业务写入直至逐项确认。语音转写作为文字提交时适用同一规则。已有附件核对、补充登记和历史清单沿现有入口。

### 短链路和固定输出

沿用 `desktop/interaction-skills.mjs`、`skills/catalog.py` 和 `source`／`versions` 的版本机制，给「对话内容转录」提供独立 Skill。四层顺序固定，在同一可恢复作业内完成。常态两次本地推理和一次集中复核。各层只允许引用本轮编号及原文、图片已识读的片段，新增条目须有依据。

| 步骤 | 处理 | 固定输出 |
| --- | --- | --- |
| 1. 文本整理 | 程序按会话梳理时间、说话人和轮次，去除回显、重试副本等重复载入的内容；保留否定、转述与纠正。 | 带轮次编号、发言者、JST 时刻的文本及附件引用。 |
| 2. 事项归纳 | 第一次本地 AI 判定现实短期个人事实，再归纳已发生的行动、委托及隐含登记线索。 | 是否有近期个人事实、「我做了什么」「我可能希望绯月做什么」「可能要登记什么」。条目带来源、事实状态、委托和依赖。近期个人事实必有个人日记意向；无近期事实仍提取其余线索。 |
| 3. 分类与抽取 | 第二次本地 AI 按模板分类，一个事实可匹配多种去向；保留原话的条件、时间和相对顺序。 | 各项类型、标题、正文、模板字段、依赖、字段来源、缺项和引用。 |
| 4. 构建、复核及汇总 | 程序应用模板默认值、核对字段和日期并去重；本地 AI 集中对照原话复核遗漏、误归属或推断。 | 最终本机候选、待补项和简短摘要，挂在原作业检查结果。仅有疑点的项重做，达到本轮时限后保留进度。 |

用户短期已发生事实默认进个人日记候选，同时保留适用专项。每项展示原话、推定、模板默认值或缺项。准备条件与真正的登记依赖分开显示；只有明确要求前置、且两项都获确认时才写既有链依赖；必需前置项被取消，关联项提示待处理。纯执行意向出现在作业摘要，超过登记职责的内容继续留作建议。项目功能想法用已有随手记字段保存项目和功能设想；用户指定花园时展示建议与待补信息，按既有流程另作具体清单。相对时间按每条发言时的东京时间，普通计划到后天，明确委托未来提醒可晚于后天。

多段发言按段引用，仍使用原发言的时间。行动、委托和隐含线索都为空时，在同一模型会话逐段补查，每段必须返回分类或明确跳过。已分类的段落直接用精简正文套用原有模板，再集中核对草稿和原话。用餐标题与原话的实际吃喝佐证一致时，补出独立吃喝候选。已发生事项的正文精简若漏掉原话中的阿拉伯数字，就保留原话。提醒日期须能从段落原话唯一确定，有疑点时标为待补或待核对。

当原话可以依据明确的相对日期及前置条件确定提醒时，以原发言的东京日期和明确条件校正草稿。确认后的清单转任务使用程序和现行业务参数模板。相同选择重复确认时返回已经保存的状态；选择发生冲突时要求重开清单。业务回执中断时沿用原提交号和节点核对。

以关窗到结果可检查为 10 分钟以内的目标，记录关窗、执行开始和结果完成时间。开工后作为不可打断的正式工作，使用自己的一次执行时限，无需借用会被前台抢占的闲时轮次。复用 `balanced-local-model.mjs` 现有工作会话、模型档位和准备逻辑，以同一会话贯穿三次推理。接线时还要保证阶段之间模型受同一作业占用，其他需要模型的请求排队。已有 `work` 仅在后续请求沿用会话时省略准备，阶段之间的占用由调度接线补齐。完成、超时或模型失败时落盘并释放。意外退出从最近有效阶段恢复；长会话分片时始终沿用同一作业。生成清单后通知一次，链接回检查结果，等待用户确认阶段不占用模型。

预备资产位于 `skills/conversation-transcription/source/`。`SKILL.md` 定义阶段条件，`local-ai.json` 载入提示和执行策略，`schemas.json` 给出常规三阶段及逐段补查的固定输出，`templates.json` 对应七个已有登记类型。资产通过绯月技能目录以同一版本读取。普通文本的关窗、调度占用、检查面板及批量提交已接入开发版，经过真实本机模型及隔离 Worker 验证。提醒时分按目标目录能力校验，原图上传仍使用现有独立登记流程。[实现与限制](reviews/CONVERSATION_TRANSCRIPTION_IMPLEMENTATION_REVIEW_2026-11-22.md)

### 明确委托未来提醒

- 在普通会话的转录链识别「帮我提醒」「到时候记得告诉我」等确实委托未来提醒的语义，也接受委婉说法和明确指向上一轮的引用。先判定是用户委托绯月新建、本人发言的范围及要提醒的对象。普通会话的提醒提案挂在原作业，独立登记入口复用原确认窗。同一句里的其他事实仍可提案，同一提醒只交给一种确认入口。提醒查询、改期、取消、假设及引用他人关于提醒的话保持自身语义。
- 时刻以用户发言时刻、原话和可明确引用的上下文为依据。明确时分和相对时间优先按 JST 换算并保留。只给日期则提案到该日。能从「明早」「明天下午早一点」等上下文拟定合理时分时，在卡片标「建议时间」让用户一起决定。未来事件若有已知的日期或时刻，可以据此拟定，缺乏可用锚点时只问具体缺项。用户实际要求的未来日期可晚于后天。已过时间不改成另一个日期或时刻。
- 确认详情复用现有提醒样式，以三项结构化字段显示「提醒时间」「标题」「内容」。标题用短行动句，正文保留用户交代的事项、先后关系、依赖、对象及材料。若用户确定了标题就保留。只提交当时显示并确认的字段，修改时间或正文后需要再次展示。比如「下周三下午三点提醒我给田中回信，先看周报第 2 页」可呈现具体日期 15:00 JST、标题「给田中回信」、正文「给田中回信前，先看周报第 2 页」。
- 主站 `reminders/model.js` 已支持 `YYYY-MM-DD` 与带时分的 JST 截止时间。既有 `reminders.create` 模板和 `main-site-task-adapter.mjs` 目前只接受日期。候选实现同步扩展现行模板和适配校验，保留旧的日期值，时分作为截止字段传给主站。原登记回执提供业务编号，隔离验收按该编号回读验证实际截止时刻。需核对登记任务目录的刷新方式以及气泡最终写入路径。既有到期检查使用轮询，提醒卡的时间字段表示登记的截止时刻。

### 明确委托登记文字或图片

- 普通交互的意图判断识别当前用户是否在请求绯月把指定内容留存，例如「这张图你替我留个档，我之后还要查」或「把上面那段留给我备查」。使用实际发言、指代和所附资料判断，现有关键词匹配可提供线索，登记意图由语义决定。在已有普通模型或本地识图处理中复用此判断。单纯看图、解释、分析、转述、否定、假设沿原交互处理。图文里的文字作为材料，不充当用户的委托。无法确定指的是哪份资料时只补问所缺对象。
- 用户明确委托的原文、所附图片及该请求所指的前文作为材料。图片用现有本地识读读取事实，区分用户说明与图像证据。默认拟一条个人日记，独立判断吃喝、运动、撸管、随手记、提醒和鱼与熊掌；只增加有依据的适用记录，用户明确限定类型或范围时按限定。单独的未来提醒委托仍为单条提醒。若同时委托留存和设提醒，可在同一转录作业展示两种内容，来源一致的候选只出现一次。
- 复用登记确认窗，一项一行显示去向、正文和原图缩略预览，复用勾选与整批决定。候选日记附图使用用户明确提供或选择的原图，并标出归属；日记正文仍保留图文中相关的信息。已有随手记等有附图能力的去向按实际用途和确认清单关联，同一批次复用同一图片回执。图片不可读时区分原图与识读内容，缺少可用文字时只补问必要内容。
- 主站日记接口接受 `photos`，当前桌宠只向 `records.create` 接线图片。候选实现沿用现有图床和登记模板，给日记模板及适配器补可选图片引用，继续接受只含标题和正文的旧登记。按用户确认的记录和图片范围走既有授权上传、引用校验及回执核对，图片处理失败保留该项待重试。

### 真实购物细节写入两本日记

- 从当前用户所说的真实购物行为提取有依据的细节。包括选购、购买、付款、取货、退换等已经发生的体验，按原话保留物品、规格、数量、金额、商家、时间或有用的体验细节。已发生的细节日期可以早于昨天，未说明日期时保持原精度。想买、假设、别人的购物及绯月推测按其原意处理。继续执行已有日记的凭据过滤。
- 同一购物事件分到两个目标。用户日记以用户口吻简洁整理，使用待确认清单；同一显式留存委托已经生成的用户日记直接纳入购物细节。绯月日记用自己的视角记听到的事实，直接进入自己的手记素材，不占用确认清单。对历史发生日有明确说法时写入正文，绯月手记依发言的 JST 日期追加。
- 用户日记复用 `diaries.create`。绯月日记复用 `personality-diary.mjs` 的草稿、稳定批次键、追加和最终回读链路。两个目标分别按同一来源事实去重和恢复。自主取材优先使用原发言里的购物事实。本流程生成的个人日记按业务回执编号关联，已知重合的购物片段合并为一处，保留其余材料。绯月日记整理提交独立于用户是否登记个人日记，独立 Paylog 取材沿用现有口径。

### 提交前整体整理

### 自主任务的 AI 拆分、快照和恢复

绯月所有自主流程共用「一次模型调用对应一个可独立跟踪的 AI 任务」的边界。业务流程保留原编号和汇总入口，复用已有 AI 询问池。独立任务可分别排队，有依赖的任务等上一步输出通过校验后再提交。业务阶段之间无需一直持有模型。

- 调用前持久化本次输入或可还原本次输入的固定版本引用、任务和尝试编号、模型档位及提示版本。快照适用原有资料访问范围，完整内容按现有本机保护方式保存。
- 调用后记实际输出或返回的部分内容、校验结果、耗时及错误或超时状态。有效产物按原编号供下一段读取。进程意外退出且没有后快照时，恢复时记录该次结果未知，保留原输入快照。已有有效输出的任务可以直接续用，失败的步骤用新的尝试编号留痕。
- 对话分析与转录按这条规则拆开。日记、评价等其他自主任务沿用各自原有业务流程与确认入口。已完成阶段的快照按照下文的下游落盘边界清理。

### 本地整理记录接手与外部工作者

- 复用未上线 `ai-requests.sqlite` 询问池作为排队和恢复入口。现有部分请求处理完即删除，需把这一步延后到下游产物落盘。快照可按业务编号和步骤编号查询；清理后仍可查询该阶段的模型、设备、尝试次数及结果摘要或错误。日记、行动评价和手记质问可在「任务执行中」按失败步骤及已有进度定位。
- 接手的原聊天已约定同一步至多 3 次尝试，含首次。暂停后不交付新调用，已开始的调用先收尾保存。按 GPU 占用阈值选择本机或允许使用的云端路径。本机 2,048／1,024 token 是实际设备的输出上限，具体请求仍受已有时限与可用上下文约束。云端串行，现有仅限本机的材料继续留在本机。
- 外部工作者按就绪工作量使用，本期上限 2 个，有一件就绪工作时用 1 个，空闲时不占名额。后续评估扩大到 5 个，届时只调整工作者容量。AI 请求统一进入现有等待队列，云端继续串行。业务链前置步骤、服务器任务回执和正式提交仍按各入口原约定。
- 验收需覆盖两件独立外部工作推进、同一步不重复领取、GPU 忙时允许外发的请求保持全局串行、本机专用输入延后、第三次失败进入待核查，以及已落盘成功结果在暂停后继续使用。

### 工作者领取事件和超时接管

提议复用 `ai-requests.sqlite` 的单写入口保存外部工作者的当前领取，按业务任务编号原子更新。工作者在现有桌面宿主中运行，由一个共用取件逻辑按新任务或输出优先选择，和 `task-lifecycle.mjs` 的服务器执行名额及 `local-task-pool.mjs` 的登记批次各自管理。当前领取只需保存阶段、持有者、领取编号和开始时间。开始、结束和接管按同一执行编号留下可查询记录，复用 `autonomous-audit.mjs` 的执行与父任务关联方式。运行时查询当前状态，避免靠回放日志计算归属。

| 事件 | 处理 |
| --- | --- |
| 领取 | 在一个事务里核对任务就绪且无有效持有者，再登记本次领取。同一任务即使有多个候选请求也只能领取一次。 |
| 完成 | 先保存实际处理结果和必要回执，再记录阶段结束并释放占用。 |
| 交给 AI | 先保存任务输入快照、业务编号、阶段编号和 AI 请求编号，持久化等待交接，再登记阶段结束并释放工作者。AI 输出就绪后，后续工作者从输出队列按原业务编号重新领取。 |
| 失败或暂时无法推进 | 保存实际错误、已完成进度和下一步去向，再结束本次领取。已有重试规则允许时回等待队列，否则保留待核查或待条件状态。任务本身仍按实际状态继续追踪。 |
| 超时接管 | 仅当最近一次有效领取没有结束记录且已超过一小时，在同一事务里标记旧领取超时、写下新领取。新工作者沿原业务和阶段编号重做当前阶段。旧工作者迟到时，其领取编号已失效，不能覆盖新结果。可能已经提交的外部动作沿原业务提交号先核对回执。 |

正常暂停或退出在保存结果或交接后释放。确认旧绯月进程已经退出后，新实例可在启动时释放旧线程的领取，记录「重启释放」，保留原任务、快照、回执和领取历史。继续处理时重新声明领取，先核对在途外部操作的原提交号。运行期间按一小时规则接管。等待 AI 的时间与工作者占用分开记录。验收覆盖 0、1、2 个工作者按需运行、第三件等待、双领取竞争、AI 交接后释放、运行时超时前禁止接管、超过一小时重新领取、重启时释放旧领取，以及旧工作者的迟到回写。

### 工作者取件倾向和日志分析专家

- 每个工作者同一时刻只持有一个有效领取。新任务工作者先看新任务，后续工作者先看 AI 输出区。优先来源没有可领取项时，可协助另一侧。各入口沿用自己的优先级与先来先服务规则，共用同一独占领取检查。工作者在结果、交接或失败处置落盘并释放后才取下一项。
- 分析专家复用定时轮询与提醒入口，默认启动间隔为一小时，可在设置中调整。每次唤醒按需创建一次巡检，同一轮尚未收尾时不重复启动，完成落盘后释放。它检查本地任务日志和领取事件，汇总实际完成、待处理与失败情况，保留可回查的任务编号和错误依据。
- 每轮固定本次结束边界，从上次成功检查的位置继续，起点最多追溯到当前时间往前 24 小时。首次巡检覆盖最近 24 小时。用时间及稳定日志位置区分同一时刻写入的多条记录。在巡检结果保存成功后更新进度，失败时保留上次进度。上次检查超过 24 小时时，本轮记录实际覆盖时段。
- 每一轮都保存本地执行记录，含实际检查时段和统计结果。无新情况时写「分析专家巡视一圈，检查了（实际时间段）的记录，无事发生」，只存本地。有新情况时通过既有入口提交汇总提醒，重复检查同一批日志时复用已提醒状态。时间段按东京时间显示。
- 验收同时准备新任务和可领取的 AI 输出，核对两个工作者各自优先取件、每人最多一项，并验证失败落盘后才释放。分析专家验收覆盖调整轮询间隔、完成即释放、按上次位置续查、首次及停机过久时的 24 小时边界、检查失败后的进度恢复、无事记录及新情况提醒去重。巡检不领取或改变业务任务。

### 同一条任务日志记录开始、内容和结束

2026-11-23 JST 复核了正式安装后的长批和窗体焦点。巡检以原周期独立启动，已挂起的巡检也可按原游标补做。手记核对每批至多提交两次尚未保存的模型调用，复用原分段、步骤摘要、待检查问题和十分钟上限。保存每步后更新已有气泡，分批交接等待现有 15 秒复查间隔。情绪补评可在同一个询问池内和手记核对交替取得时隙。点击、拖拽、切换窗口、浏览缓存新闻和录入草稿不触发取消，已提交的明确问答及指令走原前台入口。决策与现场规模见 [调度复核](reviews/FEIYUE_IDLE_SCHEDULING_REVIEW_2026-11-23.md)。

- 复用「本地复盘 → 任务日志」和现有自主行动的编号及显示字段。新增工作记录在 SQLite 中开始时插入，结束时按执行编号更新同一条。显示角色或线程、工作内容、开始与结束时间、实际结果或交接去向，以及任务、阶段或巡检编号。旧归档继续由原入口读取。巡检的「无事发生」和所查时段也显示在原巡检记录上，内容和关联编号可展开查看。
- 底层仍保留开始、结束、交接和超时等事件，展示按同一个执行编号归并为一条。工作者每次领取、AI 每次调用尝试、结果对接每次处理、分析专家每轮巡检分别使用各自的执行编号，同一业务可以按任务号追溯。只有开始的条目显示处理中或已确认的超时等实际状态。巡检自己的记录可见，后续巡检不把这些记录当成需要再次提醒的新业务结果。
- 验收逐个检查上述角色，开始后同一条日志可见且带有工作内容，结束后条目数量保持并补齐结束结果。另测失败、交接、超时、重试和无事巡检，确保执行记录能按同一业务关联，巡检自身日志不会触发循环提醒。

### 自主任务重入队与前台 6 级回退

- 后台某一步失败后，保留步骤编号、历史尝试及最近有效产物。未达到上限时按原优先级回等待队列尾部，新的调用沿用原步骤并生成新的尝试记录。更换同一失败步骤的运行设备或模型档位不重置计数；另有产物的分析、转录或业务复核各自计数。三个有效尝试均失败时停在待核查，依赖该结果的后续步骤继续等待。
- 前台 6 级优先占用下一个本机时隙。单次调用已经开始时可完成和落盘，前台随后获得时隙。允许独立外发的前台请求在本机失败后直接提交云端回退。依赖本机材料的对话可等待本机，或由用户确认补充文字后新建纯文本请求。云端保持串行，已发出的请求结束后先取等待中的前台请求，其余请求沿原顺序。同级按到达顺序。本机专用路径继续按既有资料边界处理。
- 本机失败和云端失败关联到同一前台任务，并分别保留执行路径、时间、失败阶段和实际错误。用户可以用任务号从日志核对两次尝试。验收覆盖同级后台排队、大量后台积压时的前台优先、本机成功、云端回退成功、两端失败以及本机专用路径。

### 审核后确定的调度与存储口径

1. **GPU 路由。** 在本机推理空闲、下一次准备启动前，用现有 `nvidia-smi` 读 GPU，占用检查无需加载模型。若正有绯月本机推理在跑，后台请求等到可判断，再取空闲样本。对适用的后台任务，70% 是是否转允许使用的云端路径的判断；决定走本机后，再用现有规则选 GPU／CPU 与档位。确需额外轻量 AI 时可指定 CPU 2B。前台 6 级沿用本机先试的规则。
2. **记录落点。** 建议在 `ai-requests.sqlite` 用独立业务状态与执行记录承载新增领取和可查询日志，复用既有 `action_id`／父任务编号的关联方式。原任务日志及其存档保留，界面可从现有「任务日志」查看新增记录。任务本体仍在原业务本机数据里，AI 输入／结果快照作为 JSON 负载保存，沿用本机资料保护。任务号、阶段、当前尝试次数、状态和时间使用少量可查询字段。
3. **失败回队。** 结果对接线程保存本次失败，按同一步的整数计数控制最多 3 次（含首次）。未到上限时按原优先级放回同级队尾，后继任务等有效产物。同一次重入队只安排一次，不再依赖业务入口重提。前台本机失败转云端仍按独立约定。
4. **动态长度与有限等待。** 调用前按有效上下文、素材量、输出格式及剩余时间决定送入的内容、目标长度提示和实际生成上限。GPU 2,048／CPU 1,024 token 是上限，各步骤按需要取更小值。长输入优先分段并保留来源与必要事实；结构化输出截断或不完整按失败留痕。单次调用使用有上限的设备及步骤时限，具体预算用真实设备样例校准。
5. **阶段清理。** 工作者确认依赖该快照的下游节点都已保存中间产物后，再清理已被消费的上游快照。末节点从最终结果及适用回执都落盘时起保留完整快照 7 天。到期后只清理临时快照，业务结果、任务日志、尝试次数、错误摘要及关联编号继续可查。等待中、失败待核查、回执不明或下游未落盘的阶段保留。验收覆盖末节点保留期内回读及到期清理，并确认清理后仍能从任务日志查到结果。

## 2026-11-23 JST · 本机任务生成、审核与连续修订

| 现有任务 | 4B GPU 的产出 | 2B CPU 的产出 |

每路一次执行一个步骤。独立材料可以交叠，同一材料先保存产出，再把原材料、候选和意见交下一步。通用审核通过即交付，单字段小修改通过程序校验即可交付，复杂反馈最多完整返修两次。返修稿与原稿相同会提前转最终核对。最终未通过返回具体原因，由原业务决定保留待核查或重试。专用业务仍可使用自己的分片、重试预算和确认流程。确定性格式、分类键、回执等由程序校验。

沿用单个请求库。领取时按各设备可执行的就绪请求及其优先级取项，私有知识只走内存时隙。新步骤使用生成、审核、修改、复审和终审这几种业务阶段。旧 `2-write` 恢复为首稿，`9-write` 恢复为 CPU 修订，旧核对步骤归 CPU。已有结果按原编号回读。每个任务模型分配两个计算线程，GPU 资源不足按原预算返回等待，带检查点的任务可续办。独立直连聊天、语音和视觉专用引擎沿用原入口。

### 2026-11-23 JST 三步处理与空闲领取（取代上段的阶段与路由）

同一份材料按首稿、简审、定稿运行。4B 优先领取专属首稿和定稿，仍有余力时领取共享短活。2B 先审已就绪的初稿，再做辅助工作，最后领取共享短活。在途推理完成后重新选取，两个设备可以处理不同材料。审核意见随检查点传给 4B，包括未能给出结论的情况。4B 可接受现稿、依据原文给出完整替换或明确退回。旧的待执行 9B 阶段在原检查点转为 4B 定稿，已保存的旧回包先按原阶段消费。
