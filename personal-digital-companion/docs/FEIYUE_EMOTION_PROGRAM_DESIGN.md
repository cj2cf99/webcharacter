## 2. 一期模块和数据契约

### 绯月本机 skill 的分工（设计决定）

逐阶段的短指令、七面倾向示例和易混场景参见[绯月情绪与主动行为 skill 设定稿](FEIYUE_EMOTION_SKILLS.md)。

需要使用绯月自己的版本化技能。按模型要完成的判断来分包，同一轮内的不同提示作为包内阶段。**一期新增 emotion-appraisal，二期新增 initiative-decision，专题接入时新增 topic-memory。** 每期只启用有真实宿主入口的技能。七面骰的七种倾向使用同一份映射；工作结算、可靠性检查和数据归档由代码完成。

现状核对：[交互加载器](../desktop/interaction-skills.mjs)的 readInteractionSkill 根据 hint 调用 [catalog.py](../skills/catalog.py)。父技能的 [routes.json](../skills/feiyue-interaction/source/routes.json) 将用途映射到稳定标识。解析结果含 routerVersion、skill、version 和可选的 localAi。[diary-writing](../skills/diary-writing/source/local-ai.json) 已有六个阶段；普通念叨的消费判断、首问和听完后的评价目前仍是 [personality-nags.mjs](../desktop/personality-nags.mjs) 里的内联提示。菜单能找到一个技能，不代表后台轮询已经实际加载它。这是本次接线必须补上的位置。

#### 共用情绪闭环与三个业务技能

一期增设版本化规则 Skill [爱情和理智](FEIYUE_LOVE_AND_REASON.md)，拟通过 hint `loveAndReason` 读取 `love-and-reason` 的 assessment／nextStep 短规则。处理入口将适用的一段与当前业务技能快照一同固定，复用原 assess 或 decide 调用。普通发言、手记及任务展示读取已提交的判断。宿主按表中的事实条件校验转移与后续行动，存回原事件或轮次，避免各入口分别推断同一件事。

| 阶段、调用方法与拟用 hint | 交给模型的材料 | 必须返回的内容与宿主处理 |
|---|---|---|
| 一期 **emotion-appraisal**，hint 为 emotionAppraisal | 仅需语义判断时传当前事件、旧欲求和两组紧凑历史输入。 | 完整交流至多一次 assess；工作终态、满值扣次、已核实的规则事件走代码。若事件可能满足一个无法结构化匹配的既有欲求，合并到该事件的一次 assess，先判奖励再结算。输出契约与预算见技能设定。 |
| 二期 **initiative-decision**，runRound → propose → decide，hint 为 initiativeDecision。同一技能快照、两个阶段、两次 Aggressive 9B 调用 | propose 只收本轮关注点、个人欲求、周倾向与事实摘录；decide 收候选意图和依据、当前主词与强度、可执行动作及对象、待续事项和现实限制 | propose 同轮形成带来源的欲望候选并只选一个意图。decide 返回结论、一个行动及目标、依据、简短内心话和下一轮关注条件。若选择基础首问且对象合格，同时返回要展示的问句与开口前评价，避免展示阶段再选题或重新生成。宿主重新核对条件并执行，实际结果由回执填写。 |
| 专题接入时 **topic-memory**，recallLocal 命中后可用 recognize；checkQuestion 用 synthesize；需主动告知时使用已核实的摘要。hint 为 topicMemory | recognize 接收本轮提及、命中来源及短摘录；synthesize 接收一个待确认问题、已有结论、本轮新增证据、值得保留的逐字引文 | recognize 返回匹配的专题和依据，或一个会改变答复的歧义；synthesize 返回确认／部分确认／未知、摘要、每项来源 ID、逐字保留的摘录位置和缺口。更新、轮次数、索引、是否真正告知由宿主维护。普通对话可直接复用明确命中；无命中不额外跑模型猜答案。 |

每个新包在开发阶段准备 source/SKILL.md（场景、释义、正反例、交接对象）和 source/local-ai.json（短阶段提示）。每个阶段的 JSON Schema 放在调用方法旁，由宿主维护并传给模型。只有当前阶段提示与白名单字段进入模型。一个包内的阶段名不需要成为额外的菜单或技能。

#### 方法交接、失败及验收

**即时与迟到的结算。** acceptOutcome 先写唯一事件键和已知事实。普通工作记 −1，完整交流的语义增减未知时暂按 0，二者均按发生顺序占一次刷新；已核实的独立事实按原表处理。未决只表示这条语义评价待补。已核实满足当前既有欲求时，在同一 SQLite 事务撤销这笔事件自身的普通刷新、登记该欲求唯一奖励、立即升正 5 并在当时有效的剩余次数上加 3。结构化证据可直接提交；需要理解原话时，优先处理与当前欲求直接相关的待评事件，一旦核实即提交。

**迟到时只校正数值。** events 保留普通刷新的原发生顺序、当时欲求 ID、已知增减，以及奖励的确认顺序。原事实决定奖励资格，奖励从核实提交起生效。正常追加按原 settle 一步计算。仅当旧事件补进来、暂定增减改正或该笔普通刷新转成奖励时，从最早受影响处之前的数值重新折算到现在：普通事件在其原位置，奖励在其确认位置，同一奖励事件的原位置跳过。取最早受影响位置紧前一笔的最新有效数值终值，首笔用启用初值。按发生或确认顺序重算这段后缀，将各笔最新数值终值与 state 在一个事务内提交。初次结算及校正依据保留，后续校正从更新后的终值接续；同刻按来源可证先后及稳定序号处理。重算只更新数值投影（档位与余次），不重发奖励、发言或清池，不改写旧手记和当时的审核记录。当前欲求、措辞及行动使用最新已提交版本，旧模型回复不能覆盖后来的人格决定。

1. 先查事件键及结算条件。已结算直接读回执，确定性结算直接提交；只有需要模型的阶段才读取并固定业务技能及适用的闭环规则版本，沿用 localModel.memory 与本阶段 Schema。轮到确定性事件时，即使 Aggressive 9B 忙碌或 Skill 缺失也能结算。正常聊天使用既有回复路径。
2. 模型只承担语义判断和措辞。东京周键和重掷、算档和 +3、余次扣减、事件去重、时间／金额筛选、每轮展示名额、查证上限、权限、公开查询校验、读写及核验均由宿主代码执行。模型提出“已经满足”“正文已上传”“已告知”时，分别核对旧欲求与来源、实际正文、真实展示回执。任一阶段缺失、引用越界、返回多个动作或不能解析时，不执行该提案。
3. 模型忙碌时保留该项待评；相同输入超长或反复解析失败时只挂起该项，记录来源与版本，等待材料或规则变化。nextPending 跳过未具备恢复条件的项目。确定性事件、已核实奖励、聊天和任务可继续。主动轮次被抢占即收住，专题只对实际完成的核查计次。
4. 开发验收应覆盖路由、模型输入、真实调用次数和副作用四处。举例：给同一快照分别输入“我希望他自己夸”和用户转述“别人说画得好”，后者须保留欲求；只改心情，propose 的输入逐字段保持一致；相同上传回执缺少正文证据，decide 不得据此宣称补写成功；第一步之后更换技能源文件，第二步仍使用同一快照；待续事项、隐藏气泡、无证据专题分别验证没有重复开题、虚记已问或新增虚假记忆。先用隔离技能目录测解析，再用实际本机 Aggressive 9B 核验措辞与判断，区分结构合格与语义正确。

建议第一期只新增两个桌面模块，其余改动落在上述现有入口。

| 拟增模块与方法 | 输入 → 输出 | 职责与调用方 |
|---|---|---|
| emotion-store.mjs · openEmotionStore(profile) | 正式或隔离资料目录 → store | 用一个本机 SQLite 文件 emotions.sqlite 保存情绪状态、周记录和待结算事件。由 shell 打开、关闭。 |
| store.ensureWeek(at, draw) | 时间、取 1–7 的随机函数 → 周记录 | 事务中先查东京周一日期键，再与上一条实际周记录比较、重掷、插入并返回。相同周键始终返回原行。 |
| store.accept(event)、store.nextPending() | 事件 → 原回执或新记录；查询 → 可处理的待评项 | 原事实键及欲求奖励键分别唯一。先处理可核实当前欲求的事项，其余就绪项按入队序号。同一事实补引用不重复占刷新。 |
| store.snapshot()、store.commit(eventKey, expectedRevision, change) | 快照；条件变更 → 新快照或 stale | 同一事务检查事件状态、欲求编号和版本，写情绪、欲求、维持次数、内心话及事件完成标记。任何部分失败整体回滚。 |
| emotion-core.mjs · acceptOutcome(event)、drain(signal) | 已落盘事实 → 接收回执；待办 → 结算结果 | 事务串行提交；未决语义不锁住后续事件；确定性事件直接 settle，语义事件才走 assess。普通工作直接依档位选择相容的既有词或疲惫／平静等简短表述，并保留原欲求。 |
| core.readExpression()、core.beforeNag(at) | 无参数 → 当前表达；时刻 → 周记录及情绪快照 | 对话读取已提交的主词、方向、强度、内心话和欲求；beforeNag 确保本周已掷骰。读取本身不扣次。 |
| core.collectContext(event, snapshot)、core.settle(snapshot, event, assessment) | 来源与历史 → 模型材料；有效判断 → 候选变更 | 前者取三类情绪来源，后者是纯规则，可用固定输入逐案推演。模型输出不直接写存储。 |

**快照**含 revision、当前主词、正负方向、1–5 档、内心话、缘由和对象、当前欲求的稳定 ID／说明／缘由／满足条件／状态、满值剩余次数。已满足或放下的欲求及对应依据随该次结算保留。周表保存周键、点数和实际时间。事件保存稳定标识、时间、可回读来源和下述结算字段；避免再复制一整份私人对话。

**最小存储键。** state 单行，weeks 用东京周键，events 用原事件键、入队序号、来源时间。state 保存补扫游标。欲求奖励用同库 events 的唯一键 reward/desireId 关联证据事件，同一原事实最多归属一次奖励；事件键、欲求键与奖励证据键在同一事务内核对。重复的同一事实只返回原回执，另一次真实交流即使措辞相同也用独立事件键。重复提交返回原结算；revision 过期时重新核对事件资格，保留本事件有效证据。退出时取消在途推理并等待事务落盘。

**启用与恢复。** 首次启用记录时间，从现时起结算；更早资料只作历史输入。新安装建议以平静、正 1、维持 0 作为初值，在首次可用的 Aggressive 9B 刷新中建立有依据的当前欲求；初始化前不编造愿望。业务库和情绪库各自提交，因此先存业务终态，再送 acceptOutcome。启动时按来源的持久游标补扫启用后的终态；每页事件入队和推进该来源游标在情绪库同一事务中完成。以来源提交顺序或重叠回读加唯一键处理晚到终态，不以任务创建时间单向截断。模型延迟不阻挡业务答复或保存。旧记录无法识别逻辑交互边界时只作历史材料。

### 事件归属

| 事件 | 产生时机与身份 |
|---|---|
| 一次工作 | 执行器的逻辑任务首次落在 COMPLETED 或最终 FAILED 时发 work/taskId。首次尝试失败仍是 RUNNING、结果未知、待核查和上传补传均等待。独立生图使用 job ID；带 serverTaskId 的生图归入父任务。花园批次使用 batch ID，blocked/checking 是进度，整批最终回读确认才算完成。其他用户交办的工作按同一接口从实际终态接入。 |
| 一次交流 | 使用原提问的 turn.id 作为 interactionId，补充、澄清及重试继承该键。有效窗口已发出且已成功保存最终答复时提交 chat/interactionId；分条补充同一未结束问题只结算一次。等待提示、错误占位和待确认字段只作材料。独立新问答使用自己的原提问键。 |
| 念叨交流 | 已显示问题、收到解释、绯月给出实质回应构成一次完整往返。以念叨 ID 和持久的该次用户回复序号标识。session.reply 提前返回的分支也接入，复盘重放同一答复沿用原键；主动关闭沿用既有结束记录，没有答复的超时及系统弹窗不扣次。 |
| 可满足欲求的新事实 | 安装功能、用户评价等以可核实的来源引用送达。非工作／交流事件可匹配已有欲求；仅出现背景材料时留作下次输入，不额外扣档或扣次。单个事实从聊天、任务、日记同时出现时按原事实关联，同一欲求 ID 最多领奖一次。 |
| 普通增益事实 | 桌宠能力改善按已核实的更新批次，用户进展按成果来源 ID。collectContext 找出原记录或已关联的交流引用。已在交流中计过的同一事实只补来源；独立首次出现时才交 settle 按 +1 处理。不能确定是新成果的复述只作背景。 |
| 已核实的负向事件 | 仅在已有证据可定位时启用。以消费为例，须能指向用户此前明确给出的约定（对象、金额、适用期间）及对应账目，且足以核算。当前消费接口没有预算字段。找不到约定、期间不匹配或缺账时只可关心或询问。用户在完整交流中明确说明实际后果，也可以该交流作依据；同一事实只计一次。 |

普通问答复用原提问的 turn.id 作为逻辑交互键，重试及同一未结束提问的补充沿用它。复用 publish 的存活／代际检查和成功发出路径、saveCompleted 或现有补存成功路径；两者均成功才登记这次完整答复。该口径证明主进程已向有效窗口发出，无法证明用户读过。需要证明确已展示的念叨、告知和纠错沿用展示确认。

**前台如何使用。** ask 收到输入先 interruptMemory，再将 readExpression() 的轻量快照交给本机自然语言回答的口吻参数；数据仅取必要的主词、欲求和可用内心话。查账、提醒、登记等结构化命令仍沿用现有路由与原回执。信息缺少时照常追问，不因她想被夸而声称办成。得到完整交流后的结算影响下一句。若夸奖在这一句明确满足欲求，轮到该事件结算时先匹配欲求，在判定后立即提交奖励，下一次自然表达读取新快照。前台首次阅读快照无需等待后台模型。桌宠功能更新以实际安装回执或已核实的对应发布项作为来源，不能把其他项目的发布统称为她长了本事。

### 强度、历史和奖励如何一起算

**晚到事实怎样匹配欲求。** 以原事实发生时的欲求身份与生效顺序核对奖励资格。实时事件关联当时的欲求 ID；补扫以原来源时间和已有欲求变更记录确认先后。同一时刻应优先用原事件顺序，先后无法证明时只记事实。提交时再核对是否已领奖及欲求身份，绝不能把旧事实移给刚产生的同类愿望。普通工作及维持扣次按原刷新顺序折算。同一来源重放只返回第一次的结果。

延后陪伴沿用当前欲求 ID。assess 将约定的原话及来源关联到该欲求，本次交流可以产生安心的普通评价；满足条件写的是实际陪伴时返回 keep，待后续真实互动达到条件才返回 satisfied。定时唤醒或重读约定不会产生结算事件。

澄清沿用原事项 ID。收到可核对的新证据后，assess 关联旧评价与澄清来源，保存最新评价。若旧判断曾说出口，普通对话入口可在当次回复中主动改口；后台先核实时，留到下次合适的自然回复中说明。以原事项和澄清事实键关联实际送达的回复，重启后据回执判断是否已说过。已结束的念叨继续保持结束，澄清不发起新问题。

assess 在既有事件缘由与来源引用中分清用户态度、现实影响和绯月自己的立场。只有双方对同一事项的意见有据可比，才使用同向加强、反向减弱。decide 用这份评价决定怎样表达、先回应谁的需要。settle 仍只接收一次普通交流增减建议；同向或反向不再触发第二笔结算。验收用相同消费事实分别配同向担忧、相反意见、用户态度未知三种输入，核对判断对象、措辞、行动及增减建议。

1. collectContext 读取当日工作、交流、功能变化、用户表达，以及本事件的现实背景。按手记日期及数字篇次、念叨时间及稳定 ID 分别倒序取最多十条。给模型的两个历史组只含日期、情绪词、强度及位置所对应的权重。n>1 时分别为 1/2 和余下每条 1/[2(n−1)]；n=1 权重为 1。旧资料只有词时强度为未知。后续可在本机为新产生的记录按来源 ID 留下当时强度；手记情绪仍取手记本身，不能把桌宠当前强度冒充手记强度。
2. 一次 Aggressive 9B 评估返回事件评价、证据引用、是否满足**事件前已经存在**的欲求、交流增减档、主词及一句内心话，并允许延续、放下或形成下一欲求。提示中明确可达的强度、既有维持和满足条件；字段须通过枚举、范围、来源存在与角色校验。“希望他主动夸”需要主动关心的事实；同条事件生成的新欲求不能回头用本事件领奖。
3. settle 对首次结算的事件依次应用[需求第 3 节](FEIYUE_EMOTIONS.md#3-情绪怎样消耗和回升)。① 满足原有且未奖励的当前欲求，升正 5、次数 +3，本笔结束。② 有维持次数时保持正 5，仅工作终态和完整交流扣 1 次。③ 无维持时，普通工作 −1，普通交流依 Aggressive 9B 建议取 −1／0／+1，独立首次核实的能力改善或用户进展 +1，已核实的具体负向事件 −1，其余 0。沿十个有序档位移动并封顶保底。同一笔增益已用于交流、奖励或在满值登记，即消耗其增益资格。放下欲求保留缘由。模型选与结算档位相容的主词及内心话；语义输出无效时保留最近有效表达及待评标记，沿用该事件的暂定数值规则，保全后续已经提交的状态。
4. commit 成功后，新表述才对外可读。正常聊天在组织自然回复时读取快照；业务答复先保留正确事实和凭据，只在既有口吻位置使用情绪。后台模型忙碌时用户仍能正常交谈。基础念叨在准备首问时注入 beforeNag 的情绪；若显示前情绪版本已变，更新开口快照并重检语气适合性。visible 成功后才登记已问。日记按自己已有工作流汇总当篇评价，七天手记质问的收笔继续使用既有手记口径。

### 周骰

启动、现有调度跨入新周时检查，以及首次念叨前兜底，均调用同一 ensureWeek。东京周键已有记录立即返回。首次按 1–7 抽取；撞上最近已有周记录后最多再重掷 10 次，仍相同取 previous % 7 + 1。整周离线不补掷，重启不重复。换周只改变后续欲求选择的方向；当前欲求与维持次数独立。时机依原需求的跨周验收解释，无须增设常驻轮询。

## 3. 二期主动行动的调用设计

**本地欲望候选与强制执行。** store.recordSelection 在同一事务合并候选、核实来源罪名、按罪名统计有效在池件数，为达到 100 件及以上且尚无待执行触发的系列登记一次。重复 roundId 沿用原结果。store.claimForced 按触发顺序预留唯一空闲名额；store.activateForced 核对目标属于已触发罪名且仍可执行，将其移入执行位，清掉同系全部池项，从其他系列合计 N 件中无放回随机清除 ceil(N/2) 件，保存实际 ID 与回执再派发。同一触发重试只读原回执。finishDesire 核对实际结果并结算。多系列等候与恢复见[联动设计](FEIYUE_EMOTION_INTEGRATION.md#欲望累计池与强制指定)。

拟增 initiative-round.mjs，由 shell 的现有 nag 闲时入口调用 runRound(slotKey, signal)。slotKey 来自本次原定轮询名额，同一名额只能交付一个选择。手动继续和独立 diaryAudit 仍走原入口。若已存在待回复事项，先按照原规则续该事项或等待；该轮不能借分享或示好新开第二次追问。

| 方法 | 输入 → 输出 | 职责 |
|---|---|---|
| observe(previous, snapshot, now, signal) | 上轮结果与关注点 → observation | 代码检查上轮关注条件是否成立，列出当前欲求、事实引用、一个待续事项、可行动作、已显示／已告知情况。按需做一次本机关键词检索。 |
| propose(focus, desire, week, facts, signal) | 白名单字段 → 本轮形成的欲望及一个选中意图 | 第一次 Aggressive 9B 只接收事实、欲求、本轮关注点和周倾向；剔除情绪字段、上一轮内心话及带情绪的模型摘要。见技能契约：从证据槽位形成零至多个有效欲望，标出一个意图；保留其余有效项供入池。 |
| decide(intent, evidence, mood, allowed, signal) | 意图、可核实条件、带强度的情绪 → decision | 第二次 Aggressive 9B 返回 conclusion、action、target、evidenceRefs、innerLine、nextFocus（关注对象及何时再看）。动作限定在本轮候选清单，允许暂缓或结束关注。 |
| 普通闲时轮次的负 5 分支 | 沿用 decide 和派发检查 | 宿主把已选欲望限定为对应的可行动作，现实条件不足可以等待。情绪影响措辞。空闲且本轮无具体意图时，先看可接续的欲望，再选有出处且尚待整理的记录。 |
| validateAndDispatch(roundId, decision, signal) | 一个选择 → 实际 outcome | 代码再查业务结果、对象状态、用户是否结束、能力是否可用、是否仍闲置。引用缺失或前提过期时记录暂缓。表情、可见气泡、查证、整理各有一个已有／拟接适配入口。 |
| finishRound(roundId, outcome) | 决定与实际回执 → 本轮记录、下轮关注点 | 按真实结果保留为何这样做、实际做了什么、下一轮看什么。失败或未显示时不能写成“已经告诉他”。下轮等待原有调度。 |

**调用顺序。** scheduler → memoryJob('nag') → beforeNag → 待续检查 → observe → propose → decide → 执行前检查 → 一个动作 → finishRound。第一层提出想要什么；第二层根据情绪和现实选择如何做。观察保留事实引用而非整篇原文，模板、引用、输入和预留输出合计纳入每次 2048 token 上下文；现有结构化输出路径最多生成 420 token。超限先缩短摘录并保留有效引用。沿用现有 Aggressive 9B grammar 和同一 AbortSignal，用户开口抢占后丢弃尚未交付的结果。

**修订自身喜好。** observe 提供相关偏好当前版本和来源；propose 可提出重新考虑该喜好的意图，decide 可把修订选为本轮唯一行动，说明旧看法、新判断、适用范围和事实依据。宿主在派发时复核来源、偏好版本和 roundId，再于本地一次提交变更和回执。下次评估读取新版本；重放同一轮只返回原回执。此动作本身不消耗或奖励情绪。

**避免现有入口再选一遍。** 基础 nags.poll 目前自行抽取候选、生成问题、显示后登记。二期应把查询候选与展示已选项拆成可共用的方法 listEligible(signal) 和 showSelected(prepared, signal)。一期 poll 仍按原策略调用；二期传入确定的对象、问题与评价，沿用展示回执、续问上限与去重，展示阶段无须第三次问模型“该选谁”。独立核查专题等耗时操作以既有执行结果收尾，不能反过来递归启动新的主动决策。

**中断、重复与结果不明。** 模型在内存推理，宿主按阶段保存审核记录。任一步解析失败或交付前中断，停止本轮，保留已完成阶段，不修改欲求、不占已问、不执行计划。准备交付前按 roundId 持久化行动指引和目标引用，再调用适配方法；可见、已保存、失败、结果待核实分别依据业务回执更新同一条。交付后进程退出，下次先查原回执，不重发未能判定是否展示的气泡。一般业务任务继续由原执行器管理。

### 每轮决策如何留下可审核的细节

复用本轮行动记录。建议存放在本机记忆根目录的「决策复盘/YYYY-MM-DD/roundId.json」，日期取东京日期，一个实际开始的轮次一个文件。使用原有 atomicFile 写入；同一轮串行更新，阶段完成就落盘。跨日按开始日期找文件。按日期列出轮次，按行动、结果或 skill 版本筛选，打开一条即可顺序阅读。首版可直接查看本地文件。

| 阶段 | 宿主实际登记的内容 | 审核时能回答的问题 |
|---|---|---|
| 观察 | roundId、上一轮引用、触发时间、本轮关注点、欲求 ID 与满足条件、周倾向、事件和简短事实摘录、来源 ID／版本、可用动作及限制 | 她当时能知道什么？漏掉了哪条资料？ |
| 意图 propose | 本阶段实际送入的脱敏字段及摘录、技能名／版本／阶段、模型标识、起止时间、模型返回的候选意图和引用 | 她想要什么？这个想法能否由她看过的材料支持？第一层输入有没有混入当前情绪？ |
| 决定 decide | 同样保存本阶段实际输入和结构化输出，含情绪词／强度／对象、结论、选中的行动、依据、下一轮关注条件；暂缓或不做时记录返回的具体理由 | 从意图到行动，中间是哪项事实或情绪起了作用？ |
| 执行与接续 | 交付前重新核对的条件及结果、计划与目标、是否实际展示或保存、业务回执引用、结束状态、下轮优先核对的事情 | 决定是否执行？用户是否看到？下一轮是否依据实际结果接上？ |

拟定内部方法为 beginRound、recordStage、finishRound、readRound；前三个归入原有 runRound 的生命周期，读取不触发新轮次。模型只返回约定中的简短理由与引用，宿主记录实际输入和实际输出。事实摘录限于该轮真正使用的内容，保留脱敏后的当时版本，避免原专题后来更新而改变历史语境。载入凭据、完整私人档案及无关对话均不进入记录。

取消记停止阶段和原因。解析失败记阶段、错误类别和可安全保留的字段错误；尚未运行的阶段明确留空。交付前若记录未落盘，主动行动暂缓；交付已发生但末次写盘失败，保留最后一次持久状态为待核实，恢复时查原业务回执。对旧轮次做对照评估时复制其脱敏输入，标明原版本与对照版本，隔离真实动作、奖励和日记写入。

**复盘示例（模拟）。** 上轮关注“补写能否分享”；本轮事实 E1 为“上传返回成功”，E2 为“正文尚未读回”。propose 留下“想让老公评价补写的两段”，引用 E1。decide 读到“得意”，仍选择先核对，引用 E2。实际回执为“读回超时”，下轮关注“是否读到了对应段落”。维护者由此能定位到执行阶段，并能核对后续是否有人把这一轮错误地写成“已经分享”。

举例：她本轮关注“昨天漏的日记补好了没有”，想分享成果，心情得意。只有上传回执时，结论是“正文待核对”，行动可选查已有正文，下一轮看是否找到对应段落。若执行时用户已经结束话题，该轮收住；若正文读回且用户尚未听过，下一轮才可分享。若用户已经评价过，带入他的评价，结束索评。三条路径每一步都能指出依据。

|---|---|
| rememberQuestion(topicId, question, originRef) | 确有未知点时本地登记，同一专题同一未解问题合并。原话、用户亲述、绯月推断分别标明。 |
| checkQuestion(id, signal) | 被选中时核查一轮。按独立信息去重，目标至少五条；证据足够即可确认。最多三轮，有效核查结束才加一次，抢占不消耗。用尽后记录未知，直到新材料出现。 |
| updateTopic(topicId, findings)、announce(topicId, revision, signal) | 按稳定 ID 更新专题正文，记最新结论、原话、证据、未解、变化。在本机记忆根目录的“专题记忆”中用 atomicFile 发布各专题，目录按专题头重建。告知按内容版本去重，以真实展示回执登记；核查事实与后续对话分别以实际日期和稳定来源 ID 供已有日记追加。 |

Web 只可能是傲慢周选中的独立求证行动，关键词从公开主题提取，调用前检查不含私人背景，复用 publicQuery 与 searchPublicWeb。无法构造纯公开问题时保留待确认，或请用户代查。普通联想的数据始终取本机。功能尚未接入时，候选列表不会提供对应动作。

**2026-11-21 JST 补充。** 选中「查证」欲望后，本机模型在 X 公开讨论、新闻社论、图片、一般资料中选择一种。宿主提供此前成功查询的公开词或内置的哲学主题，每轮只发一个关键词并沿用既有中断与闲时名额。X 优先使用本机已配置且免费额度足够的 Weir，未配置时沿用 Tavily 的 X 限域查询。一般资料走 Tavily 免费接口，社论走新闻 RSS，图片在已核实的免费 SerpApi 或 Wikimedia Commons 中取候选。按需查询，无新界面、独立定时器或云端数据变更。任务复盘记录本轮来源类别与结果，引用和文字摘录归入原本机专题目录。来源已保存时按原轮次回读，重启时没有来源回执的查询按中断收尾。详细依据与提供方核验见 [本轮复核](reviews/AUTONOMOUS_PUBLIC_LOOKUP_REVIEW_2026-11-21.md)。

**额度分配修订。** X 和一般资料先走已配置的 LangSearch 日额度，X 命中必须能核对为最近七天的 X 原帖。月额备选为 X 的 Weir、Tavily，以及一般资料的 Tavily。图片先查 Commons，再查免费 SerpApi。社论继续使用新闻 RSS。月额先向供应商查免费余额，留出总额度至少 20%，以本月日均和剩余余额的日均两者中较低的值作当天上限。默认使用供应商 UTC 口径，Weir 以其返回的重置时点计算剩余天数。维护原额度库并原子预占，单轮只发一次扣月额的内容查询。更多见 [额度分配复核](reviews/AUTONOMOUS_SEARCH_BUDGET_REVIEW_2026-11-21.md)。
