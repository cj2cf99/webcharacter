# 绯月正式工作队列：需求与设计

状态：待用户确认（2026-11-21 JST）。确认前不改代码。

## 1. 需求（用户原话整理）

> 能区分绯月的正式任务的工作状态（不允许打断，但原则上应该可以加入待处理队列，目前待处理队列本地扩展到 20），和她自己闲置时自发工作的状态（允许打断），这样就可以不用等待绯月 done 就直接加入待处理队列，后面怎么通信完成和确认结果就是你的问题了。完成后需要更新 infoguide 说明。
>
> 写日记、评价不算正式工作，各路轮询也不算，我的登记算，但是问答生图不算。
>
> （云端派给本机的任务）算，但是本地任务会加入待处理队列并逐个处理，不需要等闲下来再提交任务，而是看看她本地的待处理里面有没有满，没满就加进去等着处理结果。
>
> 只改本地。

### 1.1 正式工作

| 正式工作 | 来源 |
|---|---|
| 花园登记批次 | 本机 REST `POST /v1/batches` |
| 你的登记 | 随口登记、对话登记，确认后提交，由本机执行的登记任务 |
| 云端派给本机的任务 | 任务轮询接取的单条任务、任务链节点，例如服务器任务生图 |

- **不打断。** 一项开始后做到结束或暂停，期间不被打断。
- **入队只看是否满员。** 新的正式工作不等她空闲；本地待处理里还没满就加入，满了就拒绝。
- **上限 20。** 本地待处理最多 20 项，计入排队中的和正在执行的。
- **逐个处理。** 按到达顺序一项一项执行，同一时间只执行一项。
- **只改本地。** 服务器规定每台电脑最多同时接 2 个未结束任务，这条规则不变。云端任务在本地最多占 2 项，其余名额留给登记批次和你的登记。

### 1.2 非正式工作

| 类别 | 内容 | 与正式工作的关系 |
|---|---|---|
| 自发整理 | 写日记、补行动评价、补写执行评价、准备念叨、核对手记、此刻所想、情绪主动决定（含你手动点的） | 正式工作开工时，正在做的会暂停并保存草稿，回到轮询待处理，空闲后继续 |
| 轮询 | 到期事项、天气、任务、写日记等定时检查 | 保持现有行为；任务轮询改为有空位就接，见 §2.3 |
| 问答、生图 | 气泡问答、截图问答、对话生图 | 与正式工作同时进行，互不等待、互不打断 |

### 1.3 调用方与结果

- **提交后不等待。** 调用方（Claude、Codex 等）提交后立即得到编号、排队位置和当前状态，不需要等到 done。
- **完成或暂停时提醒。** 每批完成或暂停时，用托盘通知提醒一次（沿用现有做法），复盘里照常留档。
- **待回执清单。** 完成了、但调用方还没取走结果的批次，留在这个清单里。调用方下次处理相关工作时，先读这个清单，把最终回执补记到发布纪要，再标记为已取回。
- **说明文档。** 完成后更新 infoguide、`docs/LOCAL_GARDEN_API.md` 和接口契约测试。

### 1.4 显示

- 任务管理窗口的「本机执行中」页签按顺序列出全部正式工作，用徽标区分「执行中」「排队 #n」「已暂停」。
- 思考云标出「正式」或「闲时」。

### 1.5 不包含

- 正式工作之间不分优先级，也不互相抢占。
- 服务器的接取上限、主站接口、云端代码都不改。
- 不新增主动推送给 Claude 的通道，结果统一从待回执清单读取。
- 不调整问答、生图的排队方式，也不调整除任务轮询以外的轮询判断。

## 2. 设计

### 2.1 正式工作的总数与上限

在 `desktop/shell.mjs` 增加一个计数，不新建模块：

```
formalCount = 登记批次中 state ≠ done 的数量（含 queued、running、verifying、archiving、blocked）
            + 本机已接取、尚未结束的云端任务数（含你的登记执行任务）
FORMAL_LIMIT = 20
```

- 暂停（blocked）的批次仍然占名额，需要处理后才腾出位置。这一点与“满了就不加”一致，也避免暂停的批次被悄悄挤掉。
- `local-task-pool.submit` 新增参数 `hasRoom()`，满员时抛出 `{status:429}`。同一编号、同一份清单的重复提交照旧返回原批次，不受上限影响。
- 云端任务接取前也要满足 `hasRoom()` 和服务器的 2 个名额。

### 2.2 逐个执行

在 `shell.mjs` 用一个共享的 `formalBusy()` 判断：有登记批次正在执行（`localPool.active`），或有云端任务正在执行（`tasks.executingCount()`）。

- **登记批次**：开工条件 `canWork` 改为 `!quitPending && !tasks.executingCount()`。去掉原来对自发整理、轮询执行、问答、开始工作模式的等待。
- **云端任务**：`task-lifecycle.mjs` 中，已接取的任务改为串行执行，第二个任务等第一个结束再开始。执行前若有登记批次正在执行（`localPool.active`），先等它结束。
- **自发整理让路**：任一正式工作开工时调用 `interruptMemory()`。`memoryJob` 已有的中断路径会保存进度并返回 `{deferred:true}`，轮询调度会把这类任务（diary、nag、review、diaryAudit）保留在待处理队列中，空闲后从草稿继续。自发整理原本就不会在正式工作进行时开始（`memoryIdle` 已检查这一点），这部分不变。
- **问答、生图**：`screenQuestion.hasLocalWork` 不再阻止正式工作开工。正式工作也不会阻止问答，现状就是如此。

### 2.3 任务轮询：有空位就接

`task-lifecycle.mjs`：

- `canPoll` 从「`!desktopBusy()` 且完全空闲」改为：
  - 允许启动（不在退出或重启）；
  - 有空位：本地 `hasRoom()`，且已接取数小于 2；
  - 没有结果未知的旧记录：`executor.hasUnsettledWork()`、`reminderReview.hasUnknown()` 这一项沿用现有保护，结果不明时不接新任务。
- 自动接取时，不再因为 `desktopBusy()`、`activeCount()` 暂缓。接下的任务进入本地串行执行。
- `shell.mjs` 轮询调度里 `tasks` 这一项的忙碌判断，不再因正式工作进行中（`tasks.activeCount()`、`localPool.active`）、问答或开始工作模式而顺延，只看 `tasks.canPoll()`。否则正式工作一忙，任务轮询就会被推迟，与“有空位就接”矛盾。其他轮询的判断不变。
- 轮询间隔、候选读取方式和服务器接口都不变。

### 2.4 REST 接口（infoguide 版本升为 4）

| 变化 | 内容 |
|---|---|
| `POST /v1/batches` | 满员返回 `429 {error:'本地待处理已满（20/20），请稍后再提交'}`。成功的回执增加 `queue:{position,used,limit,running}`：position 从 1 开始，1 表示正在执行或下一个执行；running 是当前正在执行的正式工作标题，空闲时为 null |
| `GET /v1/batches/:id` | 未完成的批次同样附带 `queue` |
| `GET /v1/batches?unacknowledged=1` | 列出 done 或 blocked、且调用方尚未取回的批次 |
| 新增 `POST /v1/batches/:id/ack` | 无需正文，只能对 done 的批次使用，记录取回时间；重复调用返回原回执 |

- `local-batches.sqlite` 的 `batches` 表增加 `acknowledged TEXT` 列（`ALTER TABLE ... ADD COLUMN`，旧库自动补列）。历史批次一律视为已取回，不进入待回执清单。
- infoguide 的流程改为：入队后不必等待，保存编号、提交和摘要；下次开工先读待回执清单，把回执补记到发布纪要后再 ack；blocked 的批次按原来的 retry/revise 流程处理。

### 2.5 显示

- 任务管理「本机执行中」页签：在现有列表上加「执行中」「排队 #n」「已暂停」徽标，顺序与执行顺序一致。数据沿用 `local()` 已返回的批次和本机任务，再由宿主补充 `position`。
- 思考云：正式工作的标题前加「正式 ·」，自发整理的标题前加「闲时 ·」。用现有思考云的文字区分，不新增元素。
