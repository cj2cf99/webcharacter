## 实现

- `desktop/local-output-budget.mjs` 用实际模型 tokenizer 计算分析中新发言的 token，以及转录中的事项、时间、条件和证据。历史参考、模板和已由原入口处理的内容仍计入输入上下文，输出预留依据本批需要生成的正文及事项数。
- `desktop/local-model-process.mjs` 用计算出的预留决定上下文请求，沿用 CPU 1,024／GPU 2,048 token 上限及现有单次执行截止。可拆批预计超限时在生成前返回拆分结果，动态额度实际截断有独立代码。日志保留材料、输出和上下文的数字，不额外写原文。
- `desktop/conversation-transcription.mjs` 把动态截断作为一次原步骤尝试，以正常队尾顺序让行，下一次尝试用本阶段的完整额度。完整额度仍超限时沿用分片和最多三次的限制。原始标识、存储、待确认卡片和业务回执仍由已有流程管理。`desktop/task-traffic-log.mjs` 将计划内预检拆分保留为诊断记录，巡检的失败统计不计入这类拆分。

## 实际验证

同一份合成长短材料、同一 4B Vulkan 模型，依次关掉动态策略和开启策略。故障批次同样注入硬上限错误，两遍均生成运动相关候选 2 项和后续提醒 1 项，故障批次保留待复查。表中是 5 次有效模型调用，不含注入的故障调用。

| 项目 | 固定预算 | 动态预算 |
| --- | --- | --- |
| 分析的输出预留 | 1,550／1,550／1,550 | 704／832／384 |
| 转录的输出预留 | 2,048／2,048 | 640／640 |
| 上下文请求 | 四次 3,072，一次 4,096 | 五次 2,048 |
| 五次有效调用耗时合计 | 16.704 秒 | 15.394 秒 |

单轮对照的输出 token 逐项相同。上下文请求量的变化可直接核对，耗时是一次样本，真实工作负载及显存峰值未测。使用同一模型的不同输出预算，实际推理速度仍受生成长度影响。

真实 2B CPU 控制测试给了 1,763 token 的可拆材料。3 ms 返回拆分、输出 0 token。另一个极短输入要求固定长回执，在动态 384 token 额度触发截断，完整额度的再次调用成功输出 510 token，保留 CPU 1,024 的边界。队列专项另验证正常任务在再次调用前完成，原方案、步号和送达通知各保留一份。
